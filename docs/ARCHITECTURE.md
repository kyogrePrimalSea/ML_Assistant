## Source extraction approach (E01)

Spec §13.1 requires extracting from official documentation, never from memory.
For every Wave 1 library the official API reference pages are generated by
Sphinx/numpydoc from the library's own docstrings and signatures. So:

1. `tools/extract.py` introspects the **installed, pinned** package: signature
   (`inspect.signature`), numpydoc-parsed docstring sections (Parameters,
   Attributes, Returns, Methods), public methods, and for scikit-learn-style
   estimators the machine-readable `_parameter_constraints` (allowed values).
2. `tools/verify_docs.py` fetches each item's official doc URL and cross-checks
   parameter names, defaults and attributes against the extraction.
3. Discrepancies are resolved by hand in `content/extraction/overrides/<id>.yaml`
   (each override carries `source_url` and `reason`); the extractor merges
   overrides so regeneration is reproducible.
   Each patch has a `path` and an optional `op`: `set` (default; replaces the value
   at `path`), `append` (`path` names a list and `value` is a list of entries to add;
   an entry whose `name` already exists is an error) or `remove` (`path` selects a
   list entry such as `attributes[name=x]`, no `value`; absent entry is an error).
   Setting a parameter's `default` also drops that parameter's memory-address
   default-repr warning.

## Inventory entry contract

Both inventory files contain `items:` — a list of entries:

```yaml
- id: sklearn.linear_model.Ridge   # unique; the import path for code targets
  name: Ridge                       # display name as in the catalogue
  library: scikit-learn             # slug from the table above
  import_path: sklearn.linear_model.Ridge
  kind: class                       # class | function
  stage: model                      # explore|clean|transform|select|split|model|tune|evaluate|interpret
  family: Regularised               # family name; siblings doing the same job
  tracks: [standard]                # standard|unsupervised|time-series|causal|deep-learning
  archetype: model                  # transformer|resampler|selector|splitter|model|hyperparameter|
                                    # tuning|metric|diagnostic|output|composer
  doc_url: https://scikit-learn.org/stable/modules/generated/sklearn.linear_model.Ridge.html
  page: ridge                       # page id (kebab-case); several targets may share a page
  page_grouping: catalogue          # catalogue (spec says so) | proposed (needs user confirmation)
  source: catalogue                 # catalogue | supporting
  tier: core                        # core | extended (supporting cast only; catalogue items: core)
  notes: ""
```

Rules: a catalogue line naming a concept rather than a callable (e.g. "ACF/PACF
plots", "Breusch-Pagan") becomes one entry per concrete function, sharing a page.
Cross-library same-model pages (spec §3.3, e.g. LinearRegression + OLS +
`linregress`) share one `page`; groupings the spec states are `catalogue`, others
are `proposed`.

## Extraction record contract

`content/extraction/<library>/<id>.json`:

```json
{
  "id": "...", "import_path": "...", "library": "...", "library_version": "1.9.1",
  "kind": "class", "doc_url": "...", "summary": "first docstring line",
  "signature": "Ridge(alpha=1.0, *, fit_intercept=True, ...)",
  "parameters": [{
    "name": "alpha", "param_kind": "positional_or_keyword|keyword_only|var_positional|var_keyword",
    "required": false, "default": "1.0", "effective_default": null,
    "type_doc": "{float, ndarray of shape (n_targets,)}, default=1.0",
    "description": "...",
    "allowed": {"source": "constraints|docstring|none", "options": [], "intervals": [], "types": []}
  }],
  "attributes": [{"name": "coef_", "type_doc": "...", "description": "..."}],
  "methods": [{"name": "fit", "signature": "fit(X, y, sample_weight=None)", "summary": "..."}],
  "returns": [{"name": "...", "type_doc": "...", "description": "..."}],
  "extractor_version": "1", "overrides_applied": [], "warnings": []
}
```

`default` is the `repr` of the signature default, or `null` when `required` is true.
Every parameter also has `effective_default` (always `null` from introspection):
set only by an override citing the docs, for parameters whose signature default
is a sentinel such as `None` meaning "use the library default" (e.g. XGBoost
`max_depth=None` → booster default 6). Interval bounds that are unbounded are
JSON `null`.
`methods` lists public methods (no leading underscore), including inherited
library methods but excluding those inherited from `object`. `returns` applies
to functions. Missing sections are empty lists, never omitted.

## Web app (E03 onward)

- Location: `app/` (Vite + React + TypeScript). Python content tooling stays in
  `tools/`; the app never needs Python to build.
- Node: v26 via Homebrew (`/home/linuxbrew/.linuxbrew/bin/node`). CI uses the same major.
- TypeScript is 6.0.3, not 7: typescript-eslint 8.72 does not support TS 7 yet. Revisit when it does.
- Styling: Tailwind CSS v4 with the Observatory tokens as CSS custom properties;
  components from shadcn/ui on Radix, restyled with the tokens (spec §10.10).
  Icons: `@tabler/icons-react`, outline only.
- Fonts are self-hosted through `@fontsource/*` (offline PWA; no Google Fonts).
- Routing: `HashRouter` (`#/page/<id>`), because GitHub Pages can't rewrite deep links.
- Hosting: GitHub Pages from `github.com/kyogrePrimalSea/ML_Assistant`, deployed by
  GitHub Actions on push to `main`; Vite `base` is `/ML_Assistant/`.
- PWA: `vite-plugin-pwa`, precaching the app shell and all content data.
- Content data: `app/scripts/build-content.mjs` runs before `dev` and `build`. It reads
  `content/items/`, `content/questions/`, `content/derived/`, `content/schema/vocab.yaml`,
  the inventory and the extraction records, and writes static JSON to
  `app/public/data/` (generated, git-ignored):
  - `index.json` — vocab, every inventory page (id, plain name, stage, family,
    archetype, tracks, targets, has_record, reviewed; `stage` and `family` come from
    `content/taxonomy.yaml`), questions, relationships, and `taxonomy` (T038): goals, root and
    goal prompts, `views[goal]` (the elided view tree per goal, texts resolved, pages with
    `shown_as` and `pick_when`) and `labels[id]` (names and question labels of every stage, group
    and family id; `app/src/content/labels.ts` resolves them so no taxonomy id is shown).
    `app/scripts/goal-view.mjs` mirrors `tools/taxonomy.py: goal_view`; a fixture exported by
    `tools/export_goal_views.py` keeps the two equal (`tests/fixtures/taxonomy/goal-views.json`).
  - `pages/<id>.json` — one content record plus the extraction facts its slots
    reference (defaults, effective defaults for key settings).
- Radial tree layout: `app/scripts/layout-radial.mjs` runs after the content build
  (`predev`/`prebuild`) and writes `content/derived/layout-radial.json` (committed, version 2) plus a
  copy in `public/data/`. The app never computes layout at runtime (spec §7). One layout per goal
  (geometry in `app/scripts/layout-radial-core.mjs`, 1 world unit = 1 px at scale 1):
  - Depth 1 is the ring: nine stages, radius 320, 40 degrees apart, pipeline order clockwise from the top,
    labels toward the centre.
  - The children of an opened node (T038 rework) all sit on one arc around the node's own angle, so siblings
    share a radius. The radius is the smallest one, at least 70 units beyond the node, where every label box
    clears the centre, the ring, the opened ancestors and its siblings. The sector starts at
    min(120, 20 + 16(n-1)) degrees and widens to the 120 degree cap before the radius grows; it narrows only
    when a neighbour's label blocks the outer lanes. If the plain arc needs more than 140 extra units,
    alternate children stagger between R and R + one box height. Each child's label sits on its own ray,
    toward the centre or outward; the side is picked so links stay clear.
  - Links are straight. Tests check that no link crosses another and none passes through a label other than
    its own two ends (the ring-to-centre lines are dimmed and not counted). A fan is only accepted if the
    fans of the next level down also fit compactly, so every open path has a layout.
  - Label boxes are estimated from text length (`METRICS`) for both Names and Questions; the larger is stored
    (`w`, `h`, centre offset `dx`, `dy`).
  - `fits[id]` frames the tail of the open path (its stage, its parent, itself and its children). `fits.root`
    frames the whole ring. Scales reached are in the T038 run log.
  - Camera and rendering (T039; `app/src/views/camera.ts`, `RadialTree.tsx`): the camera is `screen = world * k + (x, y)`
    on one `<g class="rt-cam">`, moved imperatively (GSAP flights of 600 to 900ms on `cubic-bezier(0.22, 1, 0.36, 1)`,
    jumps with reduced motion; a drag or wheel pan cancels a flight). k is the stored fit box scaled to the canvas,
    kept in 0.85 to 1.2, so text never drops below about 13px. Where the box is still larger than the canvas, the
    camera frames the open node and as many children as fit, centred on the children's arc (`frameTail`); the rest is
    reached by drag, wheel or trackpad panning (clamped to stay near the shown nodes), by keyboard focus or selection
    (`reveal`: the least pan that puts the whole label inside the canvas) and by edge indicators ("N more", one per
    canvas side where children of the open node are cut off; a click pans toward them). A canvas resize (the page panel
    opening) refits as a jump unless the view was panned by hand. With connection lines on, k may go down to 0.25 so the
    whole ring and the line endpoints stay in view. Labels are drawn with `wrapText` and `METRICS` from the layout, so
    they fit the stored boxes in both label sets; counts, `pick_when` lines and the "Not used for this goal" note are drawn
    beside the tree items (`[data-extra-for]`), so an item's visible text is exactly its label. Dimmed stages keep their
    labels in `--text-muted`, with ring and icon at 78% opacity (3:1 or better on the canvas in both themes, tested in
    `dimming.test.ts`).
  - The goal selector, the Names | Questions toggle (`mlfg.labels` in localStorage, read and written in try/catch) and
    the derived `track` and `task` live in `ShellState`.
  - Invariants are tested in `app/src/content/layout-radial.test.ts`.
- Tests: Vitest + Testing Library (unit/component); Playwright + axe for
  end-to-end, screenshots (1440 and 1024 wide, light and dark) and accessibility.
- Commands (from `app/`): `npm run dev`, `npm run build`, `npm test`, `npm run e2e`.
- Build path (T026, `app/src/build/`): `validate.ts` implements the spec §8 rules from record
  fields only (E08 reuses it); `shape.ts` follows `rules.shape_effect` for journey tickets;
  `journey.ts` holds stops, legs and the fixed globe positions (zigzag route, constants, no runtime
  layout); `notebook.ts` makes the cells from fixed per-page templates and writes nbformat 4.5 with
  positional cell ids (byte-identical output). `app/scripts/export-demo-notebook.mjs` writes the
  demo notebook for `tests/test_notebook_demo.py`. Stops are sorted into stage order, so a fitted
  encoder (Transform) sits before the split and raises the leakage Warn the spec describes.

## Taxonomy

- File: `content/taxonomy.yaml` (goals, 9 stages, groups, families, pages; labels, prompts,
  `For` tags, `shown_as`, `pick_when`). Schema: `content/schema/taxonomy.schema.json`.
- Generated once from `docs/QUESTION_MAP.md` by `tools/gen_taxonomy.py` (T034). **From now on
  the YAML is maintained directly.** The generator is not part of the build, and re-running it
  would overwrite hand edits.
- Owner of page placement: every page sits in exactly one family (or in a group with pages
  directly, whose id then serves as the family id). Text fields are a string or a map from
  goal id to string.
- Sync test: `tests/test_taxonomy_sync.py` compares the page tables in `QUESTION_MAP.md` section 6
  with the YAML (page id, family or group id, stage, `shown_as`, `For`, `pick_when`).
  `tests/test_taxonomy_schema.py` validates the YAML against the schema. Edit both files
  together, or retire the markdown copy deliberately.
- Length and structure rules (7 children, no single-child levels, label limits) are checked
  by the validator (T035), not by these tests.
- What comes out data (T028): `tools/gen_what_comes_out.py` (seeded, `n_jobs=1`, byte-identical reruns)
  writes `content/cutscenes/outputs/<page>.json` for the four boosting pages (breast-cancer
  classification probabilities in `predict_proba` column order, and Ames-like log1p regression
  predictions, eight rows each). `build-content.mjs` already copies `content/cutscenes/` recursively, so
  the files appear at `app/public/data/cutscenes/outputs/<page>.json`; the T030 renderer fetches them there.
  The Ames sample generation is copied from `tools/gen_boosting_cutscene.py` (that script writes its file
  on import); keep the two in sync. `LGBMRegressor` also sets `min_child_samples=5` (the default 20 never
  splits on ~45 rows). The validator now returns advisory warnings (snippet lines over 79 characters)
  separately from errors; they never change the exit code.
